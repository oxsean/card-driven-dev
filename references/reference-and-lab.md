# 参照实现与真实环境

项目有能给出真实行为的参照（官方实现、真实服务、抓包、线上样本），或要在真实环境（测试机、VM、硬件）里验收时读这份。

## 参照实现

- **格式和行为以实测为准**：先用参照拿到真实输出，再写代码，不凭推测写格式。
- 第一批卡就做对照工具：调用参照、输出 golden 样本，样本检入仓库的测试数据目录。
- 测试和 golden **按字节比对**，不比「大致相同」。
- 样本要能重新生成，还要有过期检查：脚本先重新生成一遍，和检入的版本 diff，不一致就报「过期」。
- 实时对照用环境变量开关：设置了就调用参照工具对照，没设置就跳过。再写一个总脚本，负责构建工具、检查过期、带上工具跑全部测试。
- 测试**先断言样本本身**，再断言自己的输出。例如先断言所有样本里字段 X 都取同一个值，再断言自己的输出也是。这样测试编码的是证据，不是当时的假设。
- 外部依赖的测试替身按参照或实测的行为写，**连已知缺陷和限制一起模拟**，不为了让测试好过而写得比真实系统「好」。

## 真实环境

- 建 VM、网络、磁盘或改主机配置之前，先给资源和拓扑计划，等用户明确批准。批准只对那一件事有效。
- 真实环境是独占资源：各卡的这一步轮流用，同一时间只有一张卡在用。
- 改过的东西都要还原，或者写进 runbook。报告里写清跑的是哪个构建（提交号；没提交的写「工作树，基于 <提交>」）。
- 脚本先确认在哪台机器上执行（主机还是 VM）。实现 agent 的 prompt 里写明哪些命令只能在哪台机器上跑，否则探测命令会在主机上动到用户自己的程序和会话。
- 证据是**多个独立来源对得上的时间线**，例如服务端日志、协议记录、对端事件日志、系统启动时间、抓包。只有一个来源，不算证据。
- 判定逻辑或输出格式改了，真实环境里的结论就要复测，不能沿用旧的证据。

## 实现 agent 的 prompt 要多写的几条

- 对照：用哪个参照工具、要加哪些场景，输出要和参照逐字节一致。
- 环境：构建、部署、操作步骤、要记的证据；还原清单；查口令有没有出现在输出里。
- runbook 要更新哪里。
