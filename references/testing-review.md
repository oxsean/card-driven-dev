# 测试设计、回归、review 与修复

这几步决定了质量。有参照实现或真实环境时，另见 [reference-and-lab.md](reference-and-lab.md)。

## 测试设计

### 1. 证据先于假设

- 有标准答案时用它生成 golden，按字节比对，并检查样本是否过期（做法见 reference-and-lab.md）。
- 测试先断言样本本身，再断言自己的输出。

### 2. 测试替身照真实行为写（有外部依赖时）

- 外部依赖（服务、设备、第三方 API）的测试替身按实测或文档的行为写，**连已知的缺陷和限制一起模拟**。
- 替身给每个分支提供开关或模式，例如 Success / Fault / Ignored，测试按模式逐支覆盖。
- 加**计数器或状态字段**证明走的是哪条分支。只看最终结果，证明不了中间走了兜底路径。

### 3. 每条分支都测，包括「不该算」的

- 成功、失败、超时都要有测试；有并发、有外部依赖时，再加竞态、对象中途消失、依赖不可用。
- **反例测试**：明确「什么情况不能算完成」，并为它写测试。例如中间状态出现了，最终状态还没出现，不能算完成。
- 一个子测试要能证明它声称的那件事。测某条兜底路径，就要构造出只有那条路径能走通的场景，否则测的是别的路径。

### 4. 同一份输出，每条入口路径都走一遍

- 同一个产物经过不同入口时，每条路径都要测，例如 API 和 CLI，或直接打开文件和从界面点击。
  改了输出格式，所有路径都要回归。修好一条路径的改动，可能让另一条路径坏掉。

### 5. 端到端分两层

- **本地**：测试替身或本地实例，放进普通测试，可以反复跑，快。
- **真实环境**：有的话在 GATE 卡做一次，开跑前先问用户。证据要求见 reference-and-lab.md。

### 6. 按项目类型选用

- 有解析器或解码器：要有 fuzz 目标，改了就跑。
- 有时间相关逻辑：要能注入时钟、时区，写成确定性测试。判断先后（「这次之后发起的」）用进程内递增序号，不用墙钟比较：时钟精度有限，NTP 会回拨。
- 有性能要求：压测写明阈值（成功率、P95、恢复时间），按阈值判定通过与否，不能只说「跑过了」。
- 所有项目：进度记录里写测试名，便于以后核对。

## 回归

- 每张卡都跑全量，或项目约定的门禁命令：代码生成、静态检查、全部测试、对照脚本（有的话）。实现 agent 跑过之后，**主会话再跑一遍**。
- 修 bug 时先写**修改前会失败的测试**，确认它确实失败，再修。
- 隔离原因用 **A/B 对照，一次只改一个变量**：
  - 换回旧构建对比；
  - 用不进仓库的一次性构建只改一处。
  只有这样才能写「原因是……」，否则写「推断」。
- 修好一个错误结论后，**全仓库搜一遍**还有哪些地方写着旧结论，包括设计文档、任务卡、测试数据说明、调研笔记，一并改掉。
- 偶发失败的测试，在临时副本里多轮重复跑，找出原因再修，不加重试掩盖。

## Review

- 用一个**新的、只读的** agent，不让实现者自审。给它背景、真实行为和「实现声称做了什么」，让它去核对。
- **变异测试**是核心：在临时副本里故意改坏关键逻辑（去掉一个判断、把某个值恒设为 true、去掉一个分支），看测试会不会失败。
  - 失败了，说明测试有效。
  - 没失败（存活的变异），就是覆盖缺口，要补测试。
  - 报告里列出每个变异和结果。
- 实现方附检查记录（提交号、命令、结果）。提交号等于分支最新提交时，review 只重跑和问题、变异有关的测试；对不上就跑全量。合并前的全量检查照跑。
- 必查清单：
  - 「完成 / 成功」这个状态凭什么判定，有没有别的情况也满足同样的条件；
  - 并发、泄漏、超时、错误码是否和现有约定一致；
  - 文档、代码、证据三方是否一致，时间戳、秒数、编号是否对得上；
  - 有没有把推断写成实测，有没有说过头（「已查明」「全部通过」）；
  - 是否**逐字**满足卡片的验收标准，有出入就要明说；
  - 有上限类功能（限速、配额、容量）时：「先查、后扣」在并发下会超额，要用并发测试证明上限；默认值要有依据。
- 输出格式：按 high / medium / low 列出，每条写 file:line、**具体的失败场景**（输入、状态、错误结果）和修法。某个级别没有问题，要明确写「无」。

## 修复

- 把清单交回**同一个实现 agent**。它有上下文，改得最快、最准。
- 主会话在发回前**先做取舍**：
  - 哪条必须改；
  - 哪条用「接受的偏差 + 依据」处理；
  - 哪条「成本高就跳过并说明」。
  不把决定推给实现 agent。
- 每条要么改，要么写明不改的理由。改动影响真实环境结论的，要求复测。
- 改完主会话再跑全量。改动大或涉及判定逻辑时，可以再 review 一轮。
- 提交说明写清 review 修了什么。进度记录写 review 的统计（high / medium / low）和主要修复。
